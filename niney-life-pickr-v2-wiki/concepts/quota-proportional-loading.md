# 외부 API 쿼터 소비를 사용자 의도에 비례시키기

## Pattern

서울시 계열 공공 API(버스 `ws.bus.go.kr`, 지하철 swopen — 일일 1,000건 한도)를 쓰는 기능들은 전부 같은 원칙을 따른다: **업스트림 호출은 사용자의 명시적 행동(제출·선택·펼침)에만 비례해서 발생하고, 그 외에는 로컬 DB·캐시·게이트가 흡수한다.** 구체적으로 네 층이 반복된다 — (1) **정적인 것은 로컬로**: 적재 스크립트로 한 번 들여와 쿼터 0으로 서빙(지하철 검색·주변·노선·경로·혼잡), (2) **반복되는 것은 캐시로**: 30일 DB 캐시(버스 정류소 검색·노선 형상), 셀 격자 캐시(버스 주변), 블롭+stale(지하철 시간표), 15초 마이크로 캐시+in-flight 합류(지하철 실시간), (3) **트리거는 의도에 묶기**: Enter 제출형 검색(버스), 정류장·노선 "선택 시에만" 폴링, 즐겨찾기 도착 미리보기는 "펼친 행 하나만"(단일 아코디언), 크로스 도메인 검색은 "제출 게이트", 탭 비활성 시 폴링 자동 중단(`refetchIntervalInBackground: false`), (4) **마지막 방어는 게이트**: in-memory 일일 쿼터 카운터(버스 900), 스크립트 콜 상한(`verify-subway-lines` MAX_CALLS 750)과 관측 캐시(apply 재호출 0).

흥미로운 건 이 원칙이 **UX 형태까지 결정**한다는 점이다 — 버스 검색이 제출형이고 지하철 검색이 라이브인 것은 취향이 아니라 데이터 소스 비용의 직접 반영이다. 20차 라운드(2026-07-07)의 검색 UX 통일은 그 비용 차이를 없애는 게 아니라 **"타이핑=가능한 곳만 즉시, Enter·버튼=상대 도메인까지 확정"이라는 공통 문법으로 감싸서** 사용자에게 비용 구조가 보이지 않게 했다.

**2026-08 확장 — 한도는 API 마다 다르고, 그 규모가 4층의 배분을 정한다.** 서울시 1,000건/일이 아니라 에어코리아 500(개발계정) · 기상청 10,000 · VWorld 지오코딩 일 한도 · HIRA 10,000 이 각자의 숫자다. 500 인 대기는 **팬아웃 붕괴**(시도별 17콜을 '전국' 1콜 캐시 필터로 접기, 3MONTH 3콜 가중 회계)로, 10,000 인 날씨는 제출형이 아니라 **10분 폴링 허용 + 발표 슬롯 캐시**(TTL 을 "다음 발표 제공 시각까지" 로 동적 계산 — 자료의 버전이 곧 발표 시각이라는 데서 나온 하위 변형)로, 지오코딩은 **배포 시점 예산**(오프라인 소비 → 산출물 gz 커밋, 운영 0콜)으로 갈린다. 원칙은 같고 숫자가 형태를 고른다.

## Instances

- **2026-08-21~30** in [[../topics/life-map]]: 사용자 요청 경로는 전부 로컬 DB(쿼터 0). 쿼터는 적재 시점에만 — 화장실 5.3만 행의 VWorld 지오코딩을 `--max-calls`·영구 `LifeGeocodeCache`·notfound 캐시·`--offline` 로 나눠 소비하고 결과 gz 를 커밋(1일차 78.9%, 2일차 재실행 잔여), HIRA 전량 ~79콜/일 10,000. 지역 이동 검색의 VWorld search 프록시만 런타임 소비 — 250ms 디바운스 + 서버 LRU 500·10분 + 클라 staleTime 10분 + 60/분. "정적=로컬 적재" 다리를 **배포 시점 지오코딩 예산 → 산출물 커밋** 으로 확장한 인스턴스(→ [[open-data-master-load]]).
- **2026-08-21** in [[../topics/weather]]: 정적 = 245 지점표·LCC 격자 변환이 클라이언트 utils(쿼터 0, 서버는 `nx,ny` 만 받아 격자가 캐시 키) / 반복 = **발표 슬롯 캐시**(실황 매시 :10, 초단기 :45, 단기 02·05·…·23시+10분, 중기 06·18시 — 새 슬롯 NO_DATA 면 한 슬롯 이전으로 1회 폴백 5분 TTL, stale 3h/6h/24h) + AWS 전국 1콜 2분 / 트리거 = 지점 선택·전국 전망 토글 시에만 / 최후 = 일일 9,000(개발계정 10,000) + 60/분. 식단 추천 라우트가 **별도 `WeatherService` 인스턴스**를 세워 같은 키를 두 카운터가 나눠 쓰는 회계 분리가 함정.
- **2026-08-21** in [[../topics/air-quality]]: 일 500 → 서비스 한도 450(Asia/Seoul 리셋). 시도별 조회는 '전국' 1콜(673개소 ≈340KB)을 캐시해 17시도 팬아웃을 1콜로 접고, TTL 측정 10분/예보 20분/주간 60분/측정소 목록 24h + stale 폴백(3h/24h/7d) + in-flight 합류, 3MONTH 는 3콜 가중, 예보 전일 폴백 2콜 예산. 클라는 10분 refetch(비활성 탭 중단) + 상주 칩만 focus refetch. 정적 데이터(측정소 673개소)는 로컬 적재 대신 **24h 캐시**로 대체한 점이 지하철·일상지도와 다른 선택.
- **2026-07-07** in [[../topics/transit]]: 통합 13차 즐겨찾기 홈 — 도착 미리보기를 "펼친 행 하나"에만 로드+30초 폴링(단일 아코디언, 접으면 enabled=false). 데스크톱/모바일 동시 마운트도 같은 queryKey 구독이라 네트워크 1회.
- **2026-07-07** in [[../topics/transit]]: 통합 15차 크로스 검색 — 지하철 탭의 버스 크로스는 `submittedQ`(Enter/버튼 제출)에만 발화, 타이핑(라이브 q)은 절대 발화하지 않음. 버스 탭의 지하철 크로스는 로컬 DB(쿼터 0)라 제출 q에 자동. **쿼터 비대칭이 로딩 정책 비대칭으로 그대로 번역된 사례.**
- **2026-07-06~07** in [[../topics/subway]]: 지하철 도메인의 소스 3분할 — 정적(역사마스터·노선순서·혼잡 odcloud)은 적재 스크립트로 로컬 DB(쿼터 0), 실시간(도착·열차 위치)만 15초 마이크로 캐시+자체 쿼터 900+in-flight 합류, 시간표는 30일 블롭+stale 폴백. 라이브 스모크 테스트도 쿼터 초과(ERROR-337)를 "외부 상태"로 보고 skip(16eee87) — 폴링·적재가 쿼터를 소진한 날 스위트가 빨개지지 않는다.
- **2026-07-04~06** in [[../topics/bus]]: 검색은 Enter 제출형(라이브 금지 — 초기 사용자 결정), 정류소 30일 DB 캐시, 주변은 셀(0.005°) 격자 30일 캐시, 도착·위치 폴링은 정류장/노선 선택 시에만, in-memory 일일 쿼터 게이트 900.
- **2026-07-07** in [[../topics/friendly]]: `verify-subway-lines` 전량 재관측이 콜 상한(750)+관측 캐시(dry-run이 저장, `--apply`는 재호출 0)로 설계됐음에도 같은 날 폴링과 겹쳐 일일 한도를 초과 — "대량 소비 작업은 쿼터 리셋 직후·폴링 전에" 운영 수칙이 추가로 확립됨.

## What This Means

1. **쿼터는 기능 설계의 1급 제약이다** — 이 리포에서 외부 API 기능의 아키텍처 결정(로컬 적재 vs 프록시 vs 캐시 계층)은 거의 전부 "일 1,000건"이라는 숫자에서 역산된다. 새 공공 API 기능(9차 환승·출구 TAGO 등)을 붙일 때도 같은 4층(로컬/캐시/의도 트리거/게이트)을 먼저 그리는 게 맞다.
2. **비용 차이는 숨기되 없는 척하지 않는다** — 검색 UX 통일(20차)이 보여준 균형: 지하철 라이브 검색이라는 "보너스"는 유지하면서, 사용자 멘탈 모델은 하나의 문법으로 정렬. 비용이 다른 두 소스를 같은 UI 형태로 묶을 땐 트리거 시맨틱(제출)을 공통 분모로 잡는다.
3. **테스트·스크립트도 같은 예산을 쓴다** — 라이브 스모크, 전량 재관측, 브라우저 검증의 폴링이 전부 한 쿼터를 공유한다는 사실이 실측으로 드러났다(2026-07-07 소진 사건). 개발 작업 자체가 쿼터 소비자라는 인식이 운영 수칙(이른 시간 재관측·skip 처리)으로 이어졌다.

4. **숫자가 UX 를 고른다는 원칙은 한도가 커져도 유효하다** (2026-08). 1,000 이 "제출형 검색" 을 낳았듯 500 은 "팬아웃 붕괴 캐시" 를, 10,000 은 "10분 폴링 + 발표 슬롯 TTL" 을, 지오코딩 한도는 "배포 시점 예산 + 산출물 커밋" 을 낳았다. 새 공공 API 를 붙일 때 첫 질문은 여전히 "일 한도가 얼마인가" 이고, 그 답이 4층 중 어느 층을 두껍게 할지 정한다. 한도가 큰 소스일수록 게이트(최후 방어)가 얇아지고 캐시 규율(발표 슬롯)이 정교해진다.
