# 외부 API 쿼터 소비를 사용자 의도에 비례시키기

## Pattern

서울시 계열 공공 API(버스 `ws.bus.go.kr`, 지하철 swopen — 일일 1,000건 한도)를 쓰는 기능들은 전부 같은 원칙을 따른다: **업스트림 호출은 사용자의 명시적 행동(제출·선택·펼침)에만 비례해서 발생하고, 그 외에는 로컬 DB·캐시·게이트가 흡수한다.** 구체적으로 네 층이 반복된다 — (1) **정적인 것은 로컬로**: 적재 스크립트로 한 번 들여와 쿼터 0으로 서빙(지하철 검색·주변·노선·경로·혼잡), (2) **반복되는 것은 캐시로**: 30일 DB 캐시(버스 정류소 검색·노선 형상), 셀 격자 캐시(버스 주변), 블롭+stale(지하철 시간표), 15초 마이크로 캐시+in-flight 합류(지하철 실시간), (3) **트리거는 의도에 묶기**: Enter 제출형 검색(버스), 정류장·노선 "선택 시에만" 폴링, 즐겨찾기 도착 미리보기는 "펼친 행 하나만"(단일 아코디언), 크로스 도메인 검색은 "제출 게이트", 탭 비활성 시 폴링 자동 중단(`refetchIntervalInBackground: false`), (4) **마지막 방어는 게이트**: in-memory 일일 쿼터 카운터(버스 900), 스크립트 콜 상한(`verify-subway-lines` MAX_CALLS 750)과 관측 캐시(apply 재호출 0).

흥미로운 건 이 원칙이 **UX 형태까지 결정**한다는 점이다 — 버스 검색이 제출형이고 지하철 검색이 라이브인 것은 취향이 아니라 데이터 소스 비용의 직접 반영이다. 20차 라운드(2026-07-07)의 검색 UX 통일은 그 비용 차이를 없애는 게 아니라 **"타이핑=가능한 곳만 즉시, Enter·버튼=상대 도메인까지 확정"이라는 공통 문법으로 감싸서** 사용자에게 비용 구조가 보이지 않게 했다.

**2026-08 확장 — 한도는 API 마다 다르고, 그 규모가 4층의 배분을 정한다.** 서울시 1,000건/일이 아니라 에어코리아 500(개발계정) · 기상청 10,000 · VWorld 지오코딩 일 한도 · HIRA 10,000 이 각자의 숫자다. 500 인 대기는 **팬아웃 붕괴**(시도별 17콜을 '전국' 1콜 캐시 필터로 접기, 3MONTH 3콜 가중 회계)로, 10,000 인 날씨는 제출형이 아니라 **10분 폴링 허용 + 발표 슬롯 캐시**(TTL 을 "다음 발표 제공 시각까지" 로 동적 계산 — 자료의 버전이 곧 발표 시각이라는 데서 나온 하위 변형)로, 지오코딩은 **배포 시점 예산**(오프라인 소비 → 산출물 gz 커밋, 운영 0콜)으로 갈린다. 원칙은 같고 숫자가 형태를 고른다.

**2026-10 확장 — 5번째 층: 사용자가 정직하다는 가정을 버린 게이트.** 4층은 "사용자는 화면이 시키는 대로 부른다" 를 전제로 했다. 성능 감사 2차([docs/PLAN-perf-2.md](../../docs/PLAN-perf-2.md) 6차, `fd957320` 2026-10-05)는 CORS 개방 뒤의 무인증 호출자가 그 전제를 깨는 경로를 셌다 — 버스 노선상세를 프리셋 없이 300회 부르면 공유 쿼터 900 이 바닥나 **모든 사용자의 실시간 도착이 멈추고**(E-1), 가짜 측정소명 150회(약 2.5분)면 대기정보 전체가 503(E-2), 임의 중기 구역으로 날씨 9,000 고갈(E-4), 역명 순회로 IP 하나가 15분에 지하철 쿼터 소진(E-7), 짧은 업스트림 장애가 쿨다운 없이 자정까지의 503 으로 번짐(E-V2). 고친 방식이 공용 `apps/friendly/src/lib/upstream-guard.ts` 로 모였다: (a) **쿼터 칸막이** — `DailyQuota<버킷>` 으로 업스트림 서비스·오퍼레이션별 카운터(버스 search 60·arrivals 510·positions 240·route 90, 날씨 vilage 7,500·mid 1,500, 대기 realtime 100·forecast 30·weekly 30·stations 30·history 260, 바다 forecast·tide 각 2,000) — 남용된 기능만 멈춘다, 재시도도 같은 칸에 사후 가산. (b) **가짜 입력은 쿼터 0** — 측정소명은 측정소 목록 ∪ 전국 실시간 이름 화이트리스트(모르면 404), 중기 구역은 utils 지점표(모르면 400), 날짜는 clamp, '노선 없음' 은 네거티브 캐시. (c) **실패 쿨다운** — `UpstreamCooldown` 키 단위 30초→5분, 인증·일일한도 오류는 서비스 전체 5분→60분, 그동안 업스트림·쿼터 없이 stale 또는 503. (d) **IP 별 미스 예산** — 지하철 `PerClientDailyBudget`(캐시 히트는 안 셈). (e) **시간 예산** — 요청 1건(재시도 포함) `UPSTREAM_REQUEST_BUDGET_MS` 8초, 끊기면 last-known. 업스트림 대기 20~40초 → 8초, 가짜 측정소 150회 쿼터 450 소진 → 0콜, 대기 공용 키 388 → 47콜/일. 같은 원리가 VWorld 지역 검색(`LIFE_MAP_SEARCH_DAILY_BUDGET` 3,000 + in-flight, D-9)과 식단 추천의 날씨 조회(별도 `WeatherService` 를 없애고 `app.weather` 단일 인스턴스의 캐시만 엿봄, C-5)에도 들어갔다.

## Instances

- **2026-10-05 (5번째 층 — 남용·장애 방어)** in [bus](../topics/bus.md) / [subway](../topics/subway.md) / [weather](../topics/weather.md) / [air-quality](../topics/air-quality.md) / [sea](../topics/sea.md) / [transit](../topics/transit.md) (`fd957320`, `lib/upstream-guard.ts`): 위 Pattern 의 2026-10 확장 그대로. 9월 sea 인스턴스가 지적한 "4층 중 게이트가 없다·물때 임의 날짜·실패를 캐시하지 않아 장애 중 요청마다 재시도" 가 이 커밋으로 메워졌다(`SEA_QUOTA_LIMITS` + 날짜 제한 + 쿨다운). 응답 계약도 바뀌어(대기 시계열 404·중기 400·지하철 429·쿨다운 503) 외부 문서 [api-docs](../topics/api-docs.md) 에 반영됐다. 남은 후속(PLAN "리뷰 반영 → 남긴 것"): 실패 쿨다운의 기준 시각이 조회 **시작**이라 8초 예산을 다 쓰고 실패하면 쿨다운이 그만큼 짧다 — 대기·버스·지하철·날씨·AWS·바다 6곳 공통으로 실패 시점 기준으로 바꿀 것, 측정소 화이트리스트는 목록을 먼저 보고 전국 조회는 필요할 때만.
- **2026-10-05** in [life-map](../topics/life-map.md) / [meal](../topics/meal.md) (`5655abbc`·`fd957320`): 사용자 비례 런타임 소비가 남은 두 곳에도 같은 층 — VWorld 지역 검색은 고유 검색어마다 2콜이라 검색어 순회로 지오코더와 같은 키의 한도를 태울 수 있어 in-flight + 전역 일일 예산 3,000. 식단 추천은 날씨를 **부르지 않고** `app.weather` 캐시만 엿본다 — 별도 인스턴스가 카운터를 둘로 나눠 합계 18,000 을 허용하던 8월의 함정(아래 2026-08-21 weather)이 닫혔다.
- **2026-09-25 (반례 — 고정 예산 폴링)** in [parking](../topics/parking.md) (`2ff2c31`): 주차는 이 컨셉의 (3) "트리거는 의도에 묶기" 를 **의도적으로 뒤집었다**. 서울 시영 실시간 여석·공항 주차(한국공항공사 15158689·인천공항 15095047)는 `PARKING_LIVE_CRON`(기본 5분) 폴러가, 충전기 상태(환경공단 15076352)는 `EV_STATUS_CRON`(기본 10분) 폴러가 **보는 사람이 없어도** 부른다(원천당 하루 ~290콜, 충전기는 개발계정 일 1,000건 중 ~290). 사용자 요청은 폴러 메모리와 로컬 DB 만 읽어 업스트림 0콜이고(`RATE.parkingRead` 240/분), 쿼터 소비가 사용자 수와 무관한 **상수**가 된다. 이유는 데이터의 가치가 "지금 값" 이 아니라 **연속 관측**에 있어서다 — 요일×시간 평소 혼잡도(`ParkingOccupancyStat`)는 균일한 표본이 필요하고, 사용자 비례 호출로는 사람이 안 보는 새벽이 비어 통계가 기운다. 같은 칸을 4분 안에 다시 쓰지 않는 가드(재기동 직후 폴링·겹친 cron 이 표본을 부풀리지 않게)와 `onListen` 에서만 시작하는 배치([server-only-boot-effects](server-only-boot-effects.md) — 테스트·`export:openapi` 가 예산을 쓰지 않게)가 이 고정 예산을 지킨다. 원칙의 재진술: 한도 소비는 **데이터가 가치를 갖는 단위**에 비례시킨다 — 보통은 사용자 의도, 관측 누적형은 시간.
- **2026-09-24 (시간 비례 전량 캐시)** in [sea](../topics/sea.md) (`4a2bff1`): 국립해양조사원 8개 API(지수 6종·조석·이안류, 각 일 10,000건)는 요청 시점 프록시지만 캐시 단위가 사용자 입력이 아니라 **활동 전체** — 활동별 전국 지점 × 7일 예보를 한 번에 받아 1시간 캐시하고(갱신당 활동 1~6콜), 물때만 지점×날짜 12시간 캐시, 업스트림 실패 시 12시간 stale. 소비가 사용자 수가 아니라 시간에 비례해 상한이 계산 가능하다(개발계정으로 충분 — 운영계정 심의 불필요). 바다낚시 `gubun` 이 값과 무관하게 같은 1,750행을 준다는 실측으로 한 번만 부르는 것도 같은 결의 절약. 에어코리아의 "전국 1콜로 17시도 팬아웃 접기" 와 같은 형태를 활동 축에 적용한 것. **단 4층 중 마지막 층(게이트)이 없다** — 버스 900·대기 450·날씨 9,000 같은 일일 쿼터 카운터 없이 IP당 60/분(`RATE.transitRealtime`)만 막는다. 예보는 시간 비례라 괜찮지만, 물때(`/sea/tide`)는 키가 지점×**날짜**이고 날짜 형식만 검사하므로 임의 날짜로 캐시 키와 업스트림 호출을 늘릴 수 있다(물때 캐시는 스윕도 없음). 실패는 캐시하지 않아 업스트림 장애 중엔 요청마다 재시도를 다 기다린 뒤 stale 을 받는다. CORS 개방(같은 날 `1b621c4`) 뒤라 사용자 비례 부분의 게이트 부재가 더 드러난다 — 위키 27차에서 발견한 개선 후보.

## What This Means

1. **쿼터는 기능 설계의 1급 제약이다** — 이 리포에서 외부 API 기능의 아키텍처 결정(로컬 적재 vs 프록시 vs 캐시 계층)은 거의 전부 "일 1,000건"이라는 숫자에서 역산된다. 새 공공 API 기능(9차 환승·출구 TAGO 등)을 붙일 때도 같은 4층(로컬/캐시/의도 트리거/게이트)을 먼저 그리는 게 맞다.
2. **비용 차이는 숨기되 없는 척하지 않는다** — 검색 UX 통일(20차)이 보여준 균형: 지하철 라이브 검색이라는 "보너스"는 유지하면서, 사용자 멘탈 모델은 하나의 문법으로 정렬. 비용이 다른 두 소스를 같은 UI 형태로 묶을 땐 트리거 시맨틱(제출)을 공통 분모로 잡는다.
3. **테스트·스크립트도 같은 예산을 쓴다** — 라이브 스모크, 전량 재관측, 브라우저 검증의 폴링이 전부 한 쿼터를 공유한다는 사실이 실측으로 드러났다(2026-07-07 소진 사건). 개발 작업 자체가 쿼터 소비자라는 인식이 운영 수칙(이른 시간 재관측·skip 처리)으로 이어졌다.

4. **숫자가 UX 를 고른다는 원칙은 한도가 커져도 유효하다** (2026-08). 1,000 이 "제출형 검색" 을 낳았듯 500 은 "팬아웃 붕괴 캐시" 를, 10,000 은 "10분 폴링 + 발표 슬롯 TTL" 을, 지오코딩 한도는 "배포 시점 예산 + 산출물 커밋" 을 낳았다. 새 공공 API 를 붙일 때 첫 질문은 여전히 "일 한도가 얼마인가" 이고, 그 답이 4층 중 어느 층을 두껍게 할지 정한다. 한도가 큰 소스일수록 게이트(최후 방어)가 얇아지고 캐시 규율(발표 슬롯)이 정교해진다.

5. **"의도 비례" 는 수단이고 목적은 "가치 비례" 다** (2026-09-25). 주차 폴러가 보여 준 반례 — 연속 관측이 가치인 데이터(혼잡 이력)는 사용자 의도에 묶으면 오히려 망가진다. 그런 경우엔 소비를 시간 상수로 고정하고(폴러), 사용자 요청은 쿼터에서 완전히 떼어 낸다(메모리·로컬 DB 읽기). 두 설계는 대립이 아니라 같은 질문("이 데이터의 가치는 어느 단위로 생기나")의 다른 답이다. 또 외부에 API 를 연 뒤([api-docs](../topics/api-docs.md), 2026-09-24)에는 "사용자" 가 이 리포의 웹·앱 사용자만이 아니다 — 프록시형(요청 시 업스트림 호출) 라우트는 외부 호출자에게도 쿼터를 열어 주므로, 폴러·전량 캐시처럼 **소비를 요청과 분리한 설계일수록 개방에 강하다**.

6. **게이트는 마지막 층이 아니라 칸막이다** (2026-10). 9월까지 게이트는 "일일 카운터 하나" 였고, 그 하나가 바닥나면 기능 전체가 멈췄다 — 남용한 쪽과 피해를 보는 쪽이 같은 칸에 있었다. 이번 라운드는 게이트를 오퍼레이션별 칸으로 나누고(남용한 기능만 멈춤), 입력 검증으로 가짜 요청을 쿼터 앞에서 버리고(비용 0), 실패를 쿨다운으로 기억해 장애 중 재시도가 쿼터를 태우지 않게 했다. 외부에 API 를 연 뒤의 무인증 호출자는 "명시적 의도" 를 얼마든지 흉내 낼 수 있으므로, 의도 비례(1~4층)는 정직한 사용자에게 싼 화면을 주는 장치이고 칸막이·화이트리스트·쿨다운(5층)은 그렇지 않은 호출자에게서 공유 예산을 지키는 장치다. 요청 수 대신 요청의 효과를 묶는 [amplification-caps](amplification-caps.md) 와 같은 결.
