# food — 음식 카탈로그·출처 감사·식당 역검색·메뉴 칼로리 판정 엔진

**2026-10-10~10-26 변경 흡수 — 원재료 식품군 1회 분량과 식단 이름 추정이 메뉴 칼로리 계층을 재사용(`92e79e9a`, 2026-10-23)**: 식단에서 "우거지탕 칼로리가 없다"는 보고가 왔다. 원인은 둘이었다: A. 카탈로그(2,125종)에 없는 이름(우거지탕·우거지국은 짝이 없고, `FoodNutritionService` 빌려오기 규칙은 구체적 이름 → 일반 이름 쪽만이라 해당 없음), B. 원재료 DB 859종은 100g당만 있어 1인분 무게가 없음(로컬 빈 4건이 전부 반찬으로 적은 바나나·사과). 카탈로그 쪽 변경은 두 가지다. (1) **원재료 식품군 1회 분량**. [resolve.ts](../../apps/friendly/src/modules/food/engine/resolve.ts) `portionKeyFor` 가 원재료(`mfds-raw`) 행을 `RAW_CATEGORY_PORTION_KEY` 표로 식품군 키에 보낸다 — 기존 `raw_meat`(육류)·`raw_seafood`(어패류 및 기타 수산물)에 `과일류 → raw_fruit`·`채소류 → raw_vegetable`·`버섯류 → raw_mushroom`·`감자 및 전분류 → raw_potato`·`곡류 → raw_grain`·`견과 및 종실류 → raw_nut`·`두류 → raw_legume`·`난류 → raw_egg` 가 붙었다. 기본 어휘 [lexicon.ts](../../apps/friendly/src/modules/food/engine/lexicon.ts) `portionGrams` 에 2020 KDRI 식품군별 1인 1회 분량(과일 100·채소 70·버섯 30·감자 140·곡류 90·견과 10·콩 20·달걀 60g)이 들어갔다. 해조류는 마른 김(2g)·생미역(30g)이 한 군에 섞여 키가 없다. [food-serving.ts](../../apps/friendly/src/modules/food/food-serving.ts) `mealServingNutrition` 은 신규 `isRawCatalogRow` 면 **주식·반찬 구분 없이** 통상 환산(`typical_portion`, 라벨 "과일 통상 1인분 100g" — `RAW_PORTION_LABEL` 확장)을 한다(반찬 바나나 77kcal). 어휘 음식명 지정(어드민 portion, 예: 사과 → 200)이 여전히 먼저다. 메뉴 칼로리 쪽은 `computePortion` 이 같은 키를 쓰므로 원재료로 판정된 메뉴의 100g당 칩에 통상 1인분 환산이 붙을 수 있다. 골든셋 정밀도·재현율은 바꾸기 전과 같은 99.5%/98.5% 다. (2) **식단 이름 추정이 메뉴 칼로리 계층을 빌려 쓴다**. [meal](meal.md) 모듈의 신규 `MealNutritionEstimator`([meal-nutrition-estimate.ts](../../apps/friendly/src/modules/meal/meal-nutrition-estimate.ts))가 카탈로그로 못 채운 식단 항목을 규칙 엔진(`MenuNutritionResolver.resolve`) → LLM 매칭 캐시(`MenuLlmMatchService`, 표준명은 엔진 재투입) → 웹 실측 캐시(`FoodWebEstimateService`, 질의어는 [menu-nutrition.service.ts](../../apps/friendly/src/modules/food/menu-nutrition.service.ts) 의 export `webQueryFor`) 순으로 채운다. 숫자는 카탈로그·웹에서만 오고 LLM 은 가까운 음식만 고른다. 캐시 테이블(`menu_llm_matches`·`food_web_estimates`)은 맛집 메뉴와 공유하므로 같은 이름은 한 번만 묻는다. 웹 값은 100g당이라 `guessDishTypeFromName` 으로 짐작한 종류의 `portionGrams` 를 곱한다. 어드민 음식 카탈로그 화면([AdminFoodPage](../../apps/web/src/routes/admin/AdminFoodPage.tsx))에는 인식 품질과 메뉴 어휘 사이에 "열량 빈 식단 이름" 카드([MealNutritionGapSection](../../apps/web/src/routes/admin/MealNutritionGapSection.tsx))가 생겼다. 계약은 [schemas/food.ts](../../packages/api-contract/src/schemas/food.ts) `FoodAdminMealNutritionGap*`·`Routes.Food.adminMealNutritionGaps[Estimate]`, 구현은 meal 모듈이다. 어휘 화면의 portion 힌트도 "원재료 식품군 raw_meat·raw_seafood·raw_fruit·raw_vegetable 등 … 카탈로그 음식명(사과 → 200처럼 한 개 무게도)"로 바뀌었다. 운영은 마이그레이션 없이 `backfill:meal-nutrition --estimate`. 같은 기간 메뉴판 읽기 묶음(2026-10-10)은 food 모듈을 건드리지 않았다 — 메뉴 칼로리 판정은 여전히 등록 메뉴만 대상이고, 메뉴판 사진에서만 찾은 메뉴는 칩이 없다([menu-board](menu-board.md)).

**2026-10-05 변경 흡수 — 공개 메뉴 칼로리의 백그라운드 판정 상한·실패 백오프·응답 캐시(`7b060ca4`), 카탈로그 무효화 축소(`03bc43f0`)·어드민 음식 화면 디바운스(`c5052742`)**: 성능 감사 2차 7차 C-3 에서 나온 변경이다([PLAN-perf-2](../../docs/PLAN-perf-2.md), [발견 원문](../../docs/PLAN-perf-2-findings.md)). 무인증 `GET /restaurants/public/:placeId/menu-nutrition` 이 판정 못 한 메뉴로 백그라운드 LLM·웹 조회를 placeId 마다 무제한 병렬로 띄웠다(체인당 LLM 동시 4, placeId 를 훑으면 상한 없음 — 스텁 측정 동시 16). 실패한 이름은 저장하지 않아, 열람 1회(클라이언트 3초 폴링 최대 10회)가 LLM 호출 ×10 이 됐다. fatsecret 1초 간격 게이트도 4체인이 같은 시각을 보고 1초마다 4건씩 동시에 내보냈다. (1) **전역 체인 상한**. `MenuNutritionService.kickBackground` 가 프로세스 전역 [AsyncGate](../../apps/friendly/src/lib/async-gate.ts)(`BACKGROUND_CHAINS` 2·`BACKGROUND_QUEUE` 16)를 잡는다. 자리가 있으면 바로 시작하고, 대기열이 16 미만이면 줄을 선다. 가득하면 이번엔 띄우지 않고 다음 조회가 다시 본다. 동시 LLM 은 2체인 × 매칭 동시 4 = 최대 8 이다(PLAN 진행 로그의 "64→8"). (2) **판정 중 응답 30초 캐시**. `llmPending` 결과는 10분 LRU 대신 `pendingCache`(500개·30초)에 둔다. 3초 폴링이 같은 계산을 반복하지 않게 하려는 것이다. 백그라운드가 끝나면(성공이든 실패든) 지워, 다음 조회가 채워진 결과를 받는다. (3) **실패 백오프**. 신규 [menu-failure-backoff.ts](../../apps/friendly/src/modules/food/menu-failure-backoff.ts) `FailureBackoff`(LRU 5,000·기억 24시간)가 실패한 이름을 `MENU_FAILURE_BACKOFF_MS` 30분 동안 기억한다. 그동안 `lookupCached` 는 그 이름을 "결과 없음"으로 답한다(LLM 매칭 `{ hit: null, canonical: null }`, 분해·웹 `null`). 그래서 다시 묻지 않고, 응답도 `llmPending` 으로 남지 않는다. 응답 해석 실패처럼 이름에 묶인 실패(strike)가 `MENU_FAILURE_GIVE_UP_AFTER` 3번 쌓이면 '포기'를 영구 저장한다(`reason` "응답 해석 실패 3회 — 판정 포기", 매칭 없음·분해 없음). 업스트림 장애(타임아웃·429·5xx·비200)는 이름 탓이 아니므로 간격만 두고 strike 로 세지 않는다. 호출자 취소(`outerSignal.aborted`)는 기록하지 않고, 성공하면 기록을 지운다. `MenuLlmMatchService`·`MenuLlmDecomposeService`·`FoodWebEstimateService` 가 각자 인스턴스를 두고, 저장은 각자 `saveVerdict` 로 모았다. (4) **웹 조회 간격 예약**. `FoodWebEstimateService` 는 마지막 fetch 시각(`lastFetchAt`)을 보고 기다리던 방식을 버렸다. 이제 다음 자리(`nextFetchAt`)를 동기적으로 예약(`reserveFetchSlot`)하므로 동시 체인도 1초 간격을 지킨다(어간 재질의도 같은 예약을 거친다). (5) **응답 캐시 헤더**. 판정이 끝난 응답(`llmPending: false`)에 `Cache-Control: public, max-age=600` 을 붙인다([restaurant.route.ts](../../apps/friendly/src/modules/restaurant/restaurant.route.ts)) — Cloudflare·브라우저가 10분을 흡수한다. 판정 중 응답은 폴링이 새 값을 받아야 해서 뺐다. (6) **영양 점검의 카탈로그 소비**. [meal-nutrition](meal-nutrition.md) 의 한 끼 후보가 카탈로그 파생 목록(흔한 한 끼 ∩ 탐색 적격 × `mealServingNutrition` × `parseNutrientsPer100g`)을 10분 메모한다(C-7). 카탈로그를 고친 뒤 최대 10분이 늦는다. (7) **shared·어드민**. `03bc43f0`: `useCreateFoodItem`·`useUpdateFoodItem` 성공 때 `['food','admin']` 을 통째로 무효화하지 않고 `['food','admin','list']`·`['food','stats']` 만(수정이면 `['food','admin','merge-conflicts']` 도) 무효화한다. 예전에는 항목 하나를 편집할 때마다 메뉴 어휘와 인식 품질 집계(식단 기록을 읽는 무거운 조회)까지 다시 불렀다. `c5052742`: [AdminFoodPage](../../apps/web/src/routes/admin/AdminFoodPage.tsx) 의 적재 cron 미리보기는 손으로 입력할 때 300ms 디바운스(프리셋 버튼은 즉시)이고, 설정 응답이 온 뒤에만 요청한다. 입력이 반영되기 전에는 직전 식의 결과를 숨긴다. 인식 품질 version 필터도 300ms 다. 카탈로그 검색창은 `CatalogSearchInput` 으로 떼어, 300ms 멈춘 뒤 검색어와 1페이지를 한 번에 올린다 — 예전엔 2페이지 이상에서 검색을 시작하면 '옛 검색어·1페이지' 요청이 한 번 헛나갔다.

**2026-09-25~10-04 변경 흡수 — 식단 1인분 규칙 `food-serving`(`9019cf5`·`2aaaa7e`)·대표식품명/회 분류 보정(`e4ce0e6`)·분식 계통·흔한 표기·시리얼 1인분(`95ec0cd`)·이름 알레르기 단서(`e3afe9c`)·100g당 비타민·무기질(`3d067a0`)**: 식단(meal)·끼니 추천·영양소 점검이 카탈로그를 직접 소비하면서 드러난 공백을 카탈로그 쪽에서 메웠다. 공통 원칙은 **식약처 원본은 고치지 않고 우리 쪽 보정층(규칙·보정표·어휘)을 두며, 이미 적재된 행은 소급 스크립트로 맞춘다**는 것이다. ## Purpose [coverage: high — 23 sources]

- 음식 이름·별칭을 검색하고 사진 인식 결과를 `FoodItem`에 exact/alias/fuzzy 단계로 연결한다. 2026-10 부터 정확·별칭 다음에 **표기 변형·다른 이름**(계란말이 → 달걀말이, 동그랑땡 → 완자전)도 본다.
- 조리 형태 19종, 주재료 13종, 요리 계통 7종, 재료·1인분 영양·**100g당 열량**·**100g당 비타민·무기질 13종**(2026-10-04)·알레르기 슬롯·출처를 한 카탈로그에 모은다.
- **식단 기록의 한 끼 1인분**을 정한다(2026-10-02, `food-serving`) — 식약처 '식품중량'은 한 끼 양이 아니므로 원본은 두고 어휘 지정·통상 1인분으로 환산한다. 식단 저장·스냅샷 백필·끼니 추천·영양소 점검이 같은 함수를 쓴다([meal](meal.md)·[meal-nutrition](meal-nutrition.md)). → 2026-10-23: 100g당만 있는 원재료(과일·채소·버섯·감자·곡류·견과·콩·달걀)도 식품군 1회 분량으로 한 번 먹은 양을 낸다. 카탈로그 밖 식단 이름은 메뉴 칼로리의 규칙·LLM·웹 계층과 캐시를 그대로 빌려 추정한다(구현은 meal 모듈).
- 식약처 영양 표준데이터(음식 15100070·**원재료성식품 15100065**), 식품안전나라·농림 레시피, global menu canonical, 한식 800선, **코드 내장 큐레이션 표(주류·음료·공기밥)**, 수동 자료를 적재한다.
- 같은 음식에 서로 다른 source 값이 들어오면 값을 조용히 잃지 않고 field-level observation과 검토 가능한 conflict를 남긴다.
- 음식에서 역으로 메뉴·리뷰 근거가 있는 식당을 찾는다. 이는 현재 판매 보장이 아니라 수집된 evidence 검색이다.
- **맛집 상세 메뉴 탭의 칼로리 칩**을 만든다 — 크롤 메뉴명을 카탈로그에 대어 1인분/100g당/구성(세트)으로 판정하고, 규칙 밖 이름은 LLM 매칭 → 웹 실측 추정 → LLM 세트 분해로 채운다. 애매하면 항목을 뺀다(틀린 칼로리는 없는 것보다 나쁘다). 소비처는 [web](web.md)·[mobile](mobile.md)의 MenuGrid 와 [friendly](friendly.md) restaurant 모듈의 공개 엔드포인트.
- 어드민은 카탈로그·영양 coverage·source observation/conflict·적재·사진 인식 품질·**메뉴 판정 어휘**를 함께 운영한다.

- **역검색 정렬이 바뀌어 "가장 가까운 식당" 이 1등이 아닐 수 있다.** 리뷰만 있는 0m 식당보다 메뉴판+리뷰 근거의 먼 식당이 위(2026-08-24). 앱 시트 문구("근거 신뢰도와 거리 순")가 이 순서를 설명한다.
