**2026-11-06~11-14 변경 흡수 (32차) — '영양 기준 음식'으로 판단 보류를 없애고 마그네슘·아연·엽산까지 15종을 점검하며, 화면 검토로 '기록 더 필요'·곁들임·지난 조언(stale)이 생겼고, 끼니 '안 먹음'이 평균에 넣는 날을 바꾸고, 통계·추천이 같은 판정을 쓴다(`1ba0381a`·`600d15f8`·`40eb16a4`·`f4cec51d`·`27b6accd`·`ad1feff8`·`f08d7ff3`·`937f2dd2`·`0c83ddf5`·`90ccdff6`·`46134eb8`·`d772e4bb`, 2026-11-07~11-09; 문서 `de917c1e`·`96fd591e`·`2497046f`·`8f48b464`·`f66937fd`)**: (1) **원인**. 운영 '영양' 화면에서 12개 중 10개가 '판단 보류'였다. [PLAN-meal-nutrition.md](../../docs/PLAN-meal-nutrition.md) 가 원인을 다섯으로 정리했다 — ① 운영 카탈로그에 비타민·무기질이 0행(`load:food-catalog --source=nutrition --backfill-nutrition` 을 안 돌렸음, 11-07 사용자가 운영에서 실행) ② 운영 활성 카탈로그 4,812종 중 영양소가 있는 행은 약 1,260(26%) — 외식 어휘·레시피·한식 800선·원재료 행은 열량만이라 사용자 14일 열량의 32%(공기밥·치킨·해장국…)가 정보 없음, 이름 끝 맞추기로는 식단 기록 사용 53회 중 2회만 이어짐 ③ 원재료 적재기가 열량만 남김 ④ 정보 없는 열량을 0 으로 세어 '부족'이 과함 ⑤ 표준데이터 4종이 같은 24성분이라 마그네슘·아연·엽산이 없음. 사용자 "권장대로"로 1~5차를 한 번에 구현했고 결정 5건은 모두 권장안이다. (2) **영양 기준 음식**(`1ba0381a`, 규칙·LLM·어드민 세부는 [food](food.md)). 새 표 `food_nutrient_refs`(이름 단위)와 `FoodNutrientRefService.resolveIds` 가 비타민·무기질 없는 카탈로그 행·카탈로그 밖 이름을 영양소 있는 표준 음식에 잇는다(어드민 지정 → 저장 판정 → 그 자리 규칙. LLM 은 저장 뒤 백그라운드·일괄 스크립트에서만, high 확신만 채택하고 아니면 `candidateFoodId` 후보로만 남김 — `40eb16a4`). 점검 계산식이 "먹은 열량 × 기준 행의 100g당 값 ÷ 100g당 열량"(`resolveItemNutrients`)으로 바뀌었다. 자기 행이면 예전 g 환산과 값이 같고(기존 테스트 30건 그대로 통과), 1인분 무게를 몰라도 되므로 이름 추정(`foodId` null)·웹 실측 열량 항목도 영양소를 갖는다. 단백질·나트륨은 스냅샷이 먼저, 비면 기준 행의 100g당. 추정 몫이 기록 열량의 20% 이상이면 notes 한 줄. (3) **원재료 영양소·K-FIND**(`600d15f8`, 세부 [food](food.md)). 원재료 867종이 모두 영양소를 갖고(전에는 1종), 음식 적재는 K-FIND 음식 DB 엑셀(마그네슘·아연·엽산 열)이 CSV 보다 먼저다. 대표값은 같은 층 양수 **중앙값**으로 바뀌었다(해장국 철 6.83 → 2.03mg/100g, 운영 사본 28일 철 174% '충분' → 82% '조금 부족'). (4) **마그네슘·아연·엽산**. `kdri.ts` 에 2020 KDRI 원문 대조로 옮기고 defs 3행(마그네슘·엽산 `foodUpperLimit:false`, `upperLimitBasis`), 점검 12 → 15종, `NOT_MEASURED_NUTRIENTS` 10 → 7, 조언 프롬프트 v2(`OFF_LIST_RE` 에서 셋 제외), 웹·앱 화면에 자료 출처(`MEAL_NUTRIENT_DATA_SOURCES`). 운영 사본 복제본(niney@life.com) 검증: 14·28일 판단 보류 10 → **0**(정보 100%, 마그네슘·아연 95~96%). (5) **화면 검토 반영**(`f4cec51d` — 사용자가 운영 사본 화면을 Aside 로 봄). ① 11/3 조언("모자란 영양소는 없어요")이 10개 '부족' 옆에 그대로 보였다 → `GET /meals/nutrition/advice` 가 `stale`(프롬프트 버전이 다르거나 같은 기간을 오늘 다시 점검한 판정 지문 `adviceVerdict` 가 다르면 true), 웹·앱은 안내 한 줄 + 옛 조언 흐리게. ② 비타민 C 에 피자·김밥이 '한 끼로는'으로 나왔다 → 한 끼 문턱 10 → 25%, 과일·채소용 **곁들임 후보**(`common-sides.ts`·`sideSuggestions`), 조언 프롬프트 v3. ③ **사용자 결정 A안** — 판정(status)은 그대로 두고, 열량을 필요량만큼 채우면 기준에 닿는 부족·조금 부족만 `recordGap` → 화면 '기록 더 필요'(점선 주황). 기록 열량 안내 문턱 70 → 85%. ④ notes "열량을 모르는 음식 N개(…)는 점검에서 빠졌어요". ⑤ 다듬기 — 섭취량을 화면 자릿수로(`intakeForDisplay`), 기준 미만이면 99%, 조언 부족분 유효숫자 두 자리(`roundSignificant`), 6개에 못 든 대상은 요약 끝 "그 밖에 …도 기준보다 적어요", 성별·출생연도 안내 옆 설정 링크. (6) **그 밖 서버**. 합류 키에 데이터 세대를 넣어 삭제 뒤 요청이 삭제 전 계산에 합류하지 않는다(`27b6accd` — 31차 Gotcha 해결). 추론을 켠 조언이 어댑터 60초·배수 예산에 막히던 것을 고쳤다(`ad1feff8` — 호출별 `timeoutMs`, utils `thinkMaxTokens`·`thinkTimeoutMs`, 조언 대기 상한 180 → 240초). 실측(`2497046f`)상 조언 품질은 추론 단계와 무관해 권장은 '끔'이다. 가공육의 비타민 C 는 섭취량엔 세되 제안·추천 근거로 쓰지 않는다(`f08d7ff3` `isAdditiveNutrientSource`). (8) **통계가 같은 셈**(`937f2dd2`·`9080097f`·`bc24caf4`·`0c83ddf5`, 화면 `bfae13c6`·`34b47c6f`, 상세 [meal](meal.md)). 이 모듈에 `meal-nutrition-stats.ts`(`GET /meals/stats/nutrients` — 점검 함수를 고른 기간에 그대로)와 `meal-nutrition-groups.ts`(`GET /meals/stats/nutrition`)가 생겼다. 판단 보류 문턱 0.6 은 계약 상수 `MEAL_NUTRIENT_MIN_COVERAGE`. 탄단지 기준 음식(`resolveIds(…, {macros:true})`)은 통계만 쓰고 점검 판정은 그대로다. (1) **자리**. 앱 [MealNutritionView.tsx](../../apps/mobile/src/components/meal/MealNutritionView.tsx) 가 한 탭 화면에서 두 export 로 갈렸다 — `MealNutritionCheck`(영양소 점검)·`MealNutritionAdvice`(영양제 조언). ### 영양 기준 음식 — 점검이 쓰는 방식 (2026-11-07, `1ba0381a`)

연결 자체(규칙 단계·LLM·어드민 '영양 기준 음식' 절·`link:food-nutrients`)는 [food](food.md) 가 주인이다. 이 토픽에선 점검이 어떻게 쓰는지만 적는다.

- **주입**: `MealNutritionService(prisma, { refs?: Pick<FoodNutrientRefService,'resolveIds'> })`. 라우트는 `app.foodNutrientRefs`([plugins/meal.ts](../../apps/friendly/src/plugins/meal.ts) 의 전역 인스턴스)를 넘긴다. `refs` 가 없으면(옛 호출부·일부 테스트·`MealNutritionAdviceService` 의 기본 생성) 카탈로그 행 자신의 영양소만 쓴다.
- **`catalogFor(items, {macros?})`**: 항목 `foodId` 의 카탈로그 행(`CATALOG_SELECT` 에 `nameNorm`·`carbG`·`fatG`·`sugarG` 추가)을 읽는다. 이어 `refRows` 가 기준을 묻는다 — 행이 있으면 `isNutrientProfileRow`(비타민·무기질 + 100g당 열량 > 0)가 아니고 음료가 아닐 때 그 **행 이름**으로, 행이 없으면(카탈로그 밖 이름) **항목 이름**(`nameNorm`)으로. 열량 null 항목은 묻지 않는다. `resolveIds` 결과 id 를 한 번 더 읽어 이름 → 행 맵을 만든다(쿼리 2개 추가). `macros` 면 탄단지를 아는 후보 안에서 같은 일을 한 번 더 한다(통계 전용, 0c83ddf5).
- **`resolveIds`**(food 쪽): 어드민 지정 → 저장된 판정(id 가 지금도 기준 후보일 때) → 없으면 규칙을 그 자리에서(저장 안 함). 그래서 `link:food-nutrients` 를 아직 안 돌린 환경에서도 공기밥 → 쌀밥처럼 규칙으로 잡히는 음식은 바로 계산된다. 연결 표 조회가 실패하면(마이그레이션 전 DB) 경고 로그만 남기고 규칙만으로 계속한다. 기준 후보 색인은 10분 메모(`INDEX_TTL_MS`)다.
- **`resolveItemNutrients`**(점검·통계·묶음 몫이 공유): 기준 행 = 행 자신(`isNutrientProfileRow`) → 영양 기준 음식(행 이름 → 항목 이름) → 행. `factor = 먹은 열량 ÷ 기준 행 100g당 열량`. per100 영양소 = 100g당 × factor. 단백질·나트륨은 스냅샷 → 비면 기준 행의 100g당(JSON `proteinG`·`sodiumMg` → 1인분 ÷ 1인분 중량) × factor. 음료는 비타민·무기질 0. `hasVitamins` 는 defs 의 per100 키가 하나라도 있을 때.
- **식단 저장 뒤**: [meal.service.ts](../../apps/friendly/src/modules/meal/meal.service.ts) 가 영양소 없는 이름을 `nutrientRefs.schedule` 로 넘긴다(전역 1·대기열 8, 규칙 → LLM 으로 저장). 이름 추정 `estimator.schedule` 과 같은 자리다.
- **notes**: 기준 음식으로 추정한 열량이 기록 열량의 20%(`REF_NOTE_MIN_SHARE`) 이상이면 "치킨·해장국 등 N가지 음식은 비슷한 음식의 영양 구성으로 추정했어요(기록 열량의 M%)."(사용자 결정 ②).
