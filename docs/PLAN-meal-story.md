# 건강식단 스토리(PLAN)

주제 하나(나트륨 줄이기 …)를 장면 여러 장으로 넘겨 보는 손수 만든 콘텐츠 코너. 만드는 절차는
[meal-story-authoring.md](meal-story-authoring.md).

## 결정(2026-11-09, 사용자)

| 물음 | 결정 |
|---|---|
| 어디에 | **서비스 안 화면**(SNS 영상 아님) — 장면 틀 + 원고. 영상(Remotion 등)은 나중에 같은 원고로 따로 만들 수 있다 |
| 누구에게 | **누구나**(로그인 없이) — 공유 링크·카카오톡 미리보기. 내 데이터 장면(내 평균)·[이 레시피로 기록]만 로그인 |
| 첫 편 | 나트륨 줄이기 + 토마토 스파게티, **면 바꾸기는 같은 편의 덤 장면** |
| 영양 목표 | **하지 않는다** — 영양 탭 판정('많음'·'부족')이 스토리를 고른다 |
| 자리(2026-11-10) | **별도 메뉴로 두지 않고 식단 안에 융합** — 사이트 메뉴·식단 메뉴에 '건강식단' 항목이 없다. 내 판정에 맞는 이야기가 홈·영양·통계에서 맥락으로 보이고, 로그인 전에는 사이트 메뉴 '식단'이 건강식단 목록(식단의 공개 얼굴)으로 간다 |
| 움직임 | **모션 그래픽** — 슬라이드 넘기기가 아니라 애니메이션이 많은 영상처럼 이어 재생. Remotion(개인 사용 = 무료 라이선스). 예전 장면 넘기기는 '글로 보기'로 남긴다 |

## 설계

- **원고 = 서버 파일** `apps/friendly/content/meal-stories/<slug>/story.json`(git). 공유 미리보기(OG)를 서버가 만들어야 해서
  웹(`public/`)이 아니라 friendly 가 읽는다. DB·어드민 업로드는 편이 쌓여 배포 없이 올리고 싶어질 때.
- **숫자는 가리키기만** — 섭취기준(KDRI, 영양 탭과 같은 표)·식품 100g당 값(식약처 원재료성·가공식품 표준데이터 코드 →
  `build:meal-stories` 가 `foods.json` 으로)·레시피 합계·내 기록. 서버가 계산해 응답에 넣고, 출처를 값마다 단다. 시판 제품은
  여러 제품의 중앙값.
- **장면 틀 8종**(표지·큰 숫자·막대 비교·목록·재료·만드는 법·영양정보·마무리) — 편마다 화면 코드를 새로 짜지 않는다.
- **움직임 = 영상** — 장면 코드는 `apps/web/src/routes/meal-story/motion/`(Remotion 컴포지션 — 움직임은 모두 프레임으로
  계산, CSS 애니메이션 없음). 웹은 `@remotion/player` 로 재생하고(나눠 받는 청크), MP4 는 같은 코드를 `tools/meal-motion`(npm,
  워크스페이스 밖 — 렌더러·크롬·ffmpeg 가 웹·서버 설치에 섞이지 않게)이 렌더한다. 원고 장면 하나 = 영상 한 장(章), 장 길이는
  내용으로(`motion/timeline.ts`), 이웃 장은 전환 14프레임만큼 겹친다. 이 폴더는 `remotion`·`@remotion/transitions`·`react`·
  상대 경로·`@repo/api-contract` 타입만 import 한다(렌더 도구가 그대로 묶게).
- **글로 보기** — 예전 장면 넘기기(CSS 움직임: 숫자 굴러가기·막대 자라기·글 떠오르기·켄 번스, 손으로 넘김). '동작 줄이기'를
  켰거나 영상을 돌릴 수 없는 브라우저(ResizeObserver 없음)면 이게 기본. 주소 `?view=text|motion`, 장면 `?s=` 는 둘이 같이 쓴다.
- **초안은 관리자만**(목록·한 편·기록 연결). 사진은 인증 없이(`<img>`), 초안 사진도 — 글은 새지 않는다.
- **[이 레시피로 기록]** — 식단 기록은 카탈로그 행으로 영양을 계산하므로, 레시피를 카탈로그 음식(`manual`,
  `meal-story:<slug>`)으로 맞추고 그 음식으로 새 기록 draft 를 채운다. 스토리 숫자 = 기록 숫자. 이름이 겹치면 '(건강식단)'.
- **입구**(2026-11-10 바뀜 — 아래 한 일 9번) — 메뉴 항목 없이 맥락으로: 식단 홈의 건강식단 한 줄(늘 있다 — 내 14일 판정에 맞는
  이야기 먼저, 없으면 가장 새 것 + '모두 보기'), 영양 탭과 통계 영양소 흐름의 '줄이는 법 보기'·'채우는 법 보기'(같은 영양소·방향의
  게시본), 식단 안 목록 `/meal/stories`. 로그인 전에는 사이트 메뉴 '식단' → 공개 목록.
- **점검** — `check:meal-stories`(형식·가리킴·효능 단정 말투·글에 박힌 영양 값·게시 조건·사진 크기·foods.json 과 원본 대조·
  계산된 숫자와 출처 목록)와 내용 테스트(`meal-story.content.test.ts`, 같은 규칙).

      (점검 `check:meal-stories` 는 ✗), 테스트는 통과해 그대로 커밋됐다. 화면에 나가는 값은 같았다(다시 내보낸 영상 입력이
      같다). 두 편을 다시 만들고, 표준데이터가 없는 컴퓨터에서도 잡히게 내용 테스트에 '표준데이터로 푼 식품은 지금 빌더의 값
      이름을 모두 갖는다'를 더했다(`MEAL_STORY_PER100_KEYS`). 재료 값에 영양소를 더하면 모든 편을 다시 만든다.

## 남은 일

- **실기기 확인** — 저사양 안드로이드·아이폰에서 글씨 크기와 끊김(사람이 본다). 결과에 따라 글씨 하한·종이 가장자리 떨림
  (지금 초당 15회)을 조정한다.
- 취향거리: 만드는 법 장면 아래 식탁이 빈다(팁 없는 단계). 사진이 생기면 표지·단계의 폴라로이드 배치를 실제 사진으로 다시 본다
  (자리 그림으로는 변형 원고에서 확인했다).

- **첫 편 게시** — 사람: 레시피 실제 조리·분량 확인, 사진(표지 + 단계 3장), '나트륨은 어디서'·'줄이는 방법' 목록 문구의 근거
  확인(지금은 출처 없는 일반 문장), 시판 소스 150g 이 1인분으로 맞는지. 그다음 `reviewedAt`·`published`.
- **둘째 편 게시** — 사람: 실제 조리(달걀 삶는 시간·버섯 볶는 시간·분량), 사진, 목록 문구의 근거, 손으로 적은 양조간장
  값이 원본(국가표준식품성분 DB)과 맞는지, 사과·고구마 한 개 무게가 맞는지. 그다음 검수일·게시.
- **셋째 편 게시** — 사람: 실제 조리(멸치 볶는 시간·케일 양·간), 사진, 손으로 적은 값 넷(잔멸치·두부·요거트·체다)이 원본과
  맞는지, 쓰는 멸치가 잔멸치가 맞는지(큰 멸치면 칼슘이 훨씬 많다), 목록 문구의 근거. 그다음 검수일·게시.
- **앱** — 같은 API 로 앱 재생기(나중, [PLAN-mobile-meal.md](PLAN-mobile-meal.md) 후보).
- **검색 노출** — 지금은 카카오톡 미리보기(OG)만. 검색엔진용으로는 서버가 본문 글을 HTML 에 넣는 일이 더 필요하다.
- **지표** — 끝까지 본 비율·[기록] 누른 횟수(다음 주제 고르기용). 아직 세지 않는다.
- **다음 주제 후보** — 단백질 채우기, 칼륨·비타민 D(영양 탭에서 자주 '부족'인 것 — 칼륨은 신장 질환 주의가 따라붙고, 비타민 D 는
  음식만으로 채우기 어렵다). 이야기가 다루는 영양 값에 없는 영양소는 칼슘처럼 서버·계약부터 넓힌다. 새 주제는 무대 색(`TOPIC_STAGE`)과 마무리의
  짝을 함께 정한다(없으면 나트륨 색·소금통이 나온다).
- 메뉴 어휘 행이 원재료 값을 가져도(66행, 운영 사본) 반찬으로 적으면 1인분이 비는 문제는 따로 — 대표 출처가 메뉴 어휘라
  원재료 1회 분량을 못 쓴다.
