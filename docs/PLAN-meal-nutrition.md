## Context

운영 '영양' 화면에서 12개 영양소 중 10개가 '판단 보류'였다. 원인을 순서대로 확인했다.

1. **운영 카탈로그에 비타민·무기질이 0행** — 마이그레이션은 들어갔는데 `load:food-catalog --source=nutrition
   --backfill-nutrition` 이 안 돌았다. 2026-11-07 사용자가 운영에서 실행했다(코드 변경 없음).
2. **연결 부족(구조 문제)** — ①을 돌려도 운영 활성 카탈로그 4,812종 중 영양소가 있는 행은 약 1,260종(26%)뿐이다. 나머지는
   식당 메뉴 어휘(`menu-canonical`)·레시피·한식 800선·원재료 행이라 열량만 있거나 그것도 없다. 사용자 기록은 식당식
   이름이 많아 14일 열량의 32%(공기밥·치킨·해장국…)가 영양소 없는 음식이다. 공기밥↔쌀밥, 치킨↔닭튀김,
   돼지등뼈찜↔감자탕은 글자가 안 겹쳐 지금의 이름 끝 맞추기 규칙으로는 식단 기록 사용 53회 중 2회만 연결된다.
3. **원재료 적재기가 열량만 남긴다** — 원재료 CSV(15100065)에는 칼슘 2,850 · 철 2,869 · 비타민 C 2,394 ·
   칼륨 2,279 · 식이섬유 2,069행이 값을 갖는데 `food-raw-import.ts` 는 열량 중앙값만 시드한다.
4. **정보 없는 열량을 0으로 센다** — 정보 비율 60~70%면 판단은 하되 '부족'이 과하게 나온다(14일: 철·니아신 54%).
5. **'판단하지 않는 영양소' 10종** — 표준데이터 4종(15100064·65·66·70)은 모두 같은 24성분이라 마그네슘·아연·엽산이
   없다. K-FIND 전체판 음식 DB(160열)에는 음식 행에도 있다.

공공데이터 검토 전체는 메모리 `reference-food-nutrient-data-sources`(2026-11-07)와 이 문서의 '데이터 원천'.

## 목표 · 하지 않는 것

**목표**
- 판단 보류 해소: 사용자 기록 기준 정보 비율 14일 68% → ~100%, 28일 60% → ~98%(①만 실행한 상태 대비).
- 점검 영양소 12 → 15(마그네슘·아연·엽산). '판단하지 않는 영양소'는 10 → 7.
- 원칙 유지: 숫자는 공공 데이터에서만, LLM 은 "가까운 음식 고르기"만(메뉴 칼로리·이름 추정과 같은 원칙).

**하지 않는 것(이번 범위 밖)**
- 판정 규칙 변경(정보 없는 몫을 밀도로 채워 추정·60% 기준 조정) — A·B 뒤에 남는 보류를 보고 다시 정한다.
- 비타민 E·오메가3(음식 행 채움 60%), 셀레늄·B12(~19%), B6·비타민 K(2%), 요오드.
- 가공식품 DB(329,378건)·건강기능식품 DB 적재, 레시피(재료) 기반 계산, 식약처 API(15127578) 연동.

## 설계

### A. 영양 기준 음식 연결 (판단 보류의 근본 해결)

**계산식.** 영양소 = 먹은 열량 × (기준 음식의 100g당 영양소 ÷ 기준 음식의 100g당 열량). 자기 영양소가 있는 행은
기준이 자신이라 지금 식(먹은 g = 열량 ÷ 100g당 열량 × 100)과 **값이 같다** — 회귀 테스트로 고정한다. 1인분 무게를
몰라도 되므로 g 환산이 안 되던 치킨 행(중량·100g당 열량 없음)과 웹 실측 열량만 있는 이름 추정 항목도 들어온다.

**저장 — 새 표 `food_nutrient_refs`(Prisma `FoodNutrientRef`, 마이그레이션 1건)**
- `nameNorm`(unique) · `name` · `refFoodId`(FoodItem, null = 물어봤지만 없음) · `method`
  (`borrowed`·`synonym`·`rule`·`llm`·`admin`·`none`) · `confidence` · `reason` · `model` · `version` · 시각.
- 키를 **이름**으로 둔다 — 카탈로그 행(메뉴·레시피·800선)과 카탈로그 밖 이름(이름 추정 항목, `foodId` null)을
  같은 표로 푼다. 메뉴 LLM 캐시(`menu_llm_matches`)·웹 실측 캐시와 같은 "어휘 단위 영구 캐시" 모양.
- 기준 후보 = 활성 + `nutrientsPer100gJson` 있음 + 100g당 열량 > 0(식약처 음식 행, B 이후 원재료 행).

**연결 순서(결정적 → LLM → 사람)**
1. 행 자신이 영양소 + 100g당 열량을 가지면 표에 넣지 않는다(실행 때 바로 자신).
2. `borrowed` — `nutritionFrom` 이 가리키는 donor 가 후보면 그 행(불고기 ← 소불고기).
3. `synonym` — 어휘 동의어·후보의 별칭(`aliasNormsJson`) 일치 + 고정 동의 표(공기밥 → 쌀밥, 계란 ↔ 달걀 등).
4. `rule` — 핵심어(뒤 낱말) 규칙: 대상이 후보 이름으로 끝나면(소고기해장국 → 해장국, 양념순대 → 순대) 그 후보.
   범주어(`CATEGORY_WORDS`) 제외, 조리형태가 양쪽에 있으면 같아야 함. 계열 규칙(`pickNutritionDonor`)도 이 단계.
5. `llm` — 기준 후보 집합에 `pickMenuCandidates` 를 돌린 상위 후보 중 "영양 구성이 가장 비슷한 음식" 고르기.
   메뉴 LLM 매칭과 같은 채택 규칙(confidence high 만 채택, 아니면 `none` 저장 — 다시 묻지 않음, 버전 올리면 재질의),
   모델은 `OLLAMA_MENU_MATCH_MODEL`(chat 용도) 재사용, 프롬프트 v1.
6. `admin` — 어드민 지정·해제. 일괄 재실행이 덮지 않는다.

**실행 시점**
- 스크립트 `link:food-nutrients [--dry-run] [--llm] [--limit=N]` — 규칙 단계는 카탈로그 전체, LLM 은 식단 기록에
  나온 이름 + 흔한 한 끼 목록(결정 필요 1).
- 식단 저장 뒤: 새 이름이 기준을 못 찾으면 백그라운드로 묻는다 — `MealNutritionEstimator` 의 전역 1·대기열 8
  패턴(AsyncGate)을 같이 쓴다.

**점검(`analyzeMealNutrition`) 변경**
- 항목마다 기준 행 = (행 자신이 영양소 + 100g당 열량) ? 행 : ref(행 이름) ?? ref(항목 이름).
- 비타민·무기질은 위 계산식. 단백질·나트륨은 **스냅샷 우선**, 비면 기준 행의 100g당 값(1인분 ÷ 중량, 원재료는 B 의
  JSON)으로 — 운영 공기밥(단백질·나트륨 없음)이 여기서 풀린다(지난 제안 ②가 A 안으로 들어옴).
- 음료·주류 = 0 규칙, 과일·채소 공백 규칙은 유지(B 뒤엔 실제로 영양소 없는 원재료만 남는다).
- notes 에 비슷한 음식으로 추정한 몫을 밝힌다(결정 필요 2).
- 서비스는 항목 이름·행 이름으로 refs 를 한 번에, ref 행을 한 번 더 읽는다(쿼리 2개 추가).

**어드민** — 음식 페이지에 '영양 기준 음식' 절(빈 열량 이름 절 `MealNutritionGapSection` 과 같은 모양): 기록 횟수순
이름 · 현재 기준 · 방법 · 신뢰도, 바꾸기(카탈로그 검색)·해제·다시 묻기.

**효과(운영 사본 시뮬레이션, 실제 판정 함수)** — 정보 비율 14일 68 → 100%, 28일 60 → 98%. 단백질·나트륨 81 → 100%.
철 54 → 81%, 니아신 54 → 94%로 '부족' → '조금 부족'(빠진 몫을 0 으로 세던 과소 추정이 줄어듦).

### B. 원재료 영양소 보존 (+ B-2 국가표준식품성분표)

1. `food-raw-import.ts` — 열량과 **같은 행 묶음**(대표 행이 있으면 대표 행, 없으면 생것 행)에서 영양소별 중앙값을
   `nutrientsPer100gJson` 에 넣는다. 단백질·나트륨 100g당도 JSON 에 둔다(A 의 대체값 — 원재료 행은 1인분이 없어서).
2. **B-2** — 농진청 출처 행은 DB 10.4 와 이름을 대조해 마그네슘·아연·엽산을 더한다. 정규화 전 단순 대조로 1,878행 중
   1,176(63%) 일치(`멥쌀_현미_생것` ↔ `멥쌀, 현미, 생것`), `_대표_평균`·`_수입_평균` 꼬리와 `육_` 토큰 처리로 올린다.
   `-` 는 값 없음, `Tr`·`(0)` 은 0. 수산과학원 출처 행은 대조 대상이 없어 24성분만.
3. 효과 — 바나나·사과·메추리알·상추 같은 기록이 영양소를 갖는다. A 의 기준 후보도 늘어난다(닭가슴살·상추쌈 → 원재료).

### C. 마그네슘·아연·엽산

1. **데이터 키** — `NUTRIENT_KEYS` 에 `magnesiumMg`·`zincMg`·`folateUg`(μg DFE). `MFDS_NUTRIENT_CSV_HEADER` 에
   `마그네슘(mg)`·`아연(mg)`·`엽산(μg DFE)`. 표준데이터 API 에는 이 셋이 없어 API 필드 맵을 부분(Partial)으로 바꾼다.
2. **적재** — 음식 원본 기본 파일을 `data/open/food/` 의 `*_음식DB_*.xlsx`(파일명 날짜가 가장 최근) → 없으면
   기존 `mfds-nutrition.csv` 순으로 찾는다. 기존 `readTable`(XLSX 지원)·`nutritionFileRowsToRecords`(느슨한 머리글)가
   그대로 읽는다(12MB, 로컬 0.9초). upsert 의 영양소 JSON 규칙을 **빈 키만 채우는 병합**으로 바꿔 재적재가 기존 행에
   새 키를 더하게 한다(`--refresh-nutrition` 은 지금처럼 덮어쓰기). 빌린 행 복사(`backfillBorrowedNutrients`)도 키 단위 병합.
3. **기준표** — `kdri.ts` 에 magnesium·zinc·folate 의 EAR·RNI·UL 을 2020 KDRI 요약표(무기질·비타민 책자) 원문과
   대조해 옮긴다. 마그네슘 UL 은 보충제 기준, 엽산 UL 은 합성 엽산 기준이라 음식으로 '많음'을 말하지 않는다
   (`foodUpperLimit: false`), 아연 UL 은 총섭취(`true`).
4. **정의(defs)** — 세 행 추가: 영양제 권유 가능, `supplementForms`·`caution`(결정 필요 3), `produceSensitive`(마그네슘·
   엽산 true), `typicalFoods`.
5. **계약·화면** — `MealNutrientKey`(api-contract)에 3개 추가, `NOT_MEASURED_NUTRIENTS` 에서 3개 제거. utils 는 키별 표가
   없고 웹·앱은 서버 `label` 로 그리므로 화면 코드는 거의 그대로(육안 확인만). 옛 조언 저장본의 분석 스냅샷은
   키가 부분집합이라 재검증을 통과한다(테스트로 고정). `export:openapi` 재생성.
6. **조언** — `OFF_LIST_RE` 에서 마그네슘·아연·엽산을 빼고 시스템 프롬프트의 예시를 고친다.
   `MEAL_NUTRITION_ADVICE_VERSION` 2(같은 날 저장본 캐시가 자연히 무효화), `probe:meal-nutrition` 으로 kimi-k3 문장 검사.
7. **출처 표기** — 영양 화면 면책 문구 아래 "영양성분: 식품영양성분 데이터베이스(식약처 K-FCDB) · 국가표준식품성분표
   10개정판(농촌진흥청)", `docs/data-sources.md` 에 파일·받는 곳·조건.
8. **효과(시뮬레이션, A 연결 가정, 기준은 30-49세 남녀 중 낮은 값의 근사 — 구현 때 원문 값으로 다시 잰다)** —
   마그네슘 정보 95~96% · 권장량의 57~60%(부족), 아연 95~96% · 125~136%(충분), 엽산 100% · 30~32%(부족).
